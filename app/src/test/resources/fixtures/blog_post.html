Why We Rewrote Our Build System in a Weekend

By Jane Example, March 3

For three years our continuous integration pipeline took forty minutes on a good day. Every engineer on the team had a story about pushing a one-line change, going to lunch, and coming back to a flaky failure in a test suite that had nothing to do with their change.

We had tried the usual fixes. We added caching, we split the test suite into shards, and we bought bigger machines. Each of these helped for a few weeks, and then the build crept back up as the codebase grew.

What was actually slow

When we finally profiled the pipeline end to end, the answer was embarrassing. More than half of the time was spent resolving dependencies that had not changed, because our build tool invalidated its cache whenever a lockfile timestamp changed, even when the contents were identical.

The fastest build step is the one you never run.

The fix itself was small: hash the contents instead of trusting modification times. But getting there required untangling a pile of shell scripts that nobody fully understood anymore.

  • Content hashing for every input file
  • A single entry point instead of eleven scripts
  • Remote caching shared between developers and CI
build --cache=remote --hash=content ./...

Today a typical pull request builds in under four minutes. More importantly, people trust the build again, which means they stop re-running it just in case.
